Defesa do Castelo

Um jogo de Tower Defense Medieval
Atividade 02 — Criando um Jogo · HTML5 Canvas + JavaScript
Josué Oliveira  ·  Roberto Rawlison
O Jogo

O que é

  • Tower defense que roda 100% no navegador (HTML + JavaScript)
  • Defenda o castelo de 10 ondas de bárbaros
  • Apenas torres automáticas — sem personagem controlável
  • Moedas ao derrotar inimigos → comprar e melhorar torres
  • Mapa gerado proceduralmente, com múltiplos caminhos
  • Escolhemos Tower Defense no lugar do Tetris — cobre os mesmos conceitos do guia
Decisões de projeto

Stack & regras

  • HTML5 Canvas + JS puro (módulos ES6, sem framework)
  • Sprites PNG externos (+ fallback de retângulos)
  • Castelo com HP = 100; vitória na onda 10
  • 3 torres: arqueiro · besta · catapulta (com upgrade)
  • 3 bárbaros: martelo (básico), furioso (veloz), machado (tanque)
  • Grid 36×21 · células de 48px
Ferramentas & agentes

Como construímos

  • Claude Code (CLI) — agente único que lê/escreve arquivos e roda comandos
  • Modelos Claude: Sonnet (rápido, maioria das edições) e Opus (planejamento)
  • ChatGPT — geração das imagens de referência dos sprites (pixel art)
  • Destaque: o agente fez perguntas antes de codar e gerou um plano de projeto
Ponto de partida

Experiência prévia

  • HTML / JavaScript: básica
  • Desenvolvimento de jogos: nenhuma
  • Conceitos novos para nós:
game loopdelta time geração proceduralpathfinding (BFS) Web AudiolocalStorage
Etapa 1

Base do jogo

  • Geração de mapa + caminhos + autotile dos tiles
  • Torres com upgrade e projéteis (catapulta com tiro parabólico)
  • 3 inimigos, 10 ondas e a fase de construção entre ondas
  • Condições de vitória/derrota pelo HP do castelo
  • Código modular (main, map, maze, tower, enemy, wave, ui, render…)
Etapa 2

Níveis & pontuação

  • Dificuldade Fácil / Difícil (muda o nº de caminhos) + regenerar labirinto
  • Pontuação pela vida do castelo preservada — 100% = partida perfeita
  • Medalhas: Perfeito · Ouro · Prata · Bronze · Sobreviveu
  • High scores: ranking das melhores tentativas
Etapa 3

Loop de arcade

  • Tela de abertura — aguarda o jogador interagir para começar
  • Game over → mostra resultado e volta ao início
  • Attract mode — demonstração jogada sozinha por um "bot"
  • Loop clássico: abertura → attract → high scores → abertura
Etapa 4

Outras adições

  • Persistência: ranking no localStorage
  • Sprites PNG direcionais (4 direções)
  • Áudio: música + efeitos MP3 (matar, onda, upgrade, dano, vitória/derrota)
  • Extras: velocidade 1x–4x, indicadores de surgimento, servidor sem cache
Não foi linear

Retrabalho & dificuldades

  • Cache do navegador: botões "paravam de funcionar" → servidor no-cache
  • Diminuir o mapa quebrou a geração dos caminhos → revertido
  • Calibragem do zig-zag dos caminhos — feita por tentativa/iteração
  • Frestas entre tiles (linhas verdes) — ajustes de renderização
  • O agente diagnosticou a maioria a partir da descrição do sintoma (e de prints)
Conclusões · 1

Aprendizado

  • A falta de experiência não impediu — o agente comprimiu a curva de aprendizado
  • Aprendemos: game loop, módulos, localStorage, Web Audio, servir via HTTP
  • Sem agentes? Não nesse prazo nem nesse acabamento, dado o ponto de partida
Conclusões · 2

Código & compreensão

  • Código razoavelmente legível e modular (configs centralizadas)
  • Refatoração seria saudável se crescesse (main.js concentra muito)
  • Déficit de compreensão: entendemos no geral, mas não a fundo as partes algorítmicas (geração de mapa, BFS)
  • Mudanças pequenas: conseguiríamos sozinhos · estruturais: difícil sem o agente
Conclusões · 3

Como julgamos sucesso

  • Julgamos sobretudo pelo comportamento na tela — funcional, mas limitado
  • "Funciona" ≠ "código bom": validar de verdade exige entender o que foi feito
  • Atenção: estudar fundamentos · déficit de compreensão · validação real
  • Experiência geral: muito positiva e produtiva
